# 🗂️ WORK-BOARD 方法論（完整版・繁體中文）

> 這份是「方法論說明書」，不是某個專案的看板本體。
> 目的：讓任何團隊理解「多人 / 多 AI session 並行開發時，怎麼用一份純文字檔避免互相打架」，並能在自己的 repo 照著建一份。
>
> 適用對象：用 Claude Code / Cursor / 其他 AI agent 協作開發、且**常常同時開多個對話視窗（session）或多個 git worktree / 分支**在改同一個 repo 的團隊或個人。

---

## 一、它解決什麼問題

當你開始用 AI agent 開發，會很自然地**同時開好幾個對話視窗**：A 在改結帳、B 在改後台、C 在寫文件。每個 AI session 都是「失憶的」——它只知道自己這個對話裡發生的事，**完全不知道另一個視窗正在動哪些檔案**。於是會出現：

| 災難 | 發生原因 |
|---|---|
| 兩個 session 同時改到同一支檔案 → merge 衝突 / 互相覆蓋 | 沒人知道對方在動這塊 |
| 重複做同一件事 | A 做完的功能，B 不知道又重做一遍 |
| 改了 X 卻不知道 Y 正依賴 X 的舊行為 | 沒有「射程範圍」概念 |
| 接手的人從 0 問起 | 上一個 session 的進度沒留在固定地方 |
| 誤刪別人還在用的分支 | 靠記憶或舊紀錄判斷「這分支沒人用了」 |

**WORK-BOARD 就是一張貼在公佈欄上的紙**：誰正在做什麼、做到哪、會碰到哪些檔案。開工前看一眼，就不會撞車。

> 核心觀念一句話：**把「誰在做什麼」變成一份所有 session 都看得到、且會主動維護的純文字 SSOT（單一真相來源 Single Source of Truth）。**

### 什麼時候*不需要*用（先講邊界，避免過度工程）

這套東西有維護成本，不是每個專案都該上。符合以下任一就先別用：你永遠只開**一個**視窗、線性做事；團隊就一個人且不會同時開多分支；專案小到心裡記得住誰在動哪。

**真正需要它的訊號**：你開始**同時**開 2 個以上視窗 / worktree 改同一個 repo、或多人協作、或曾經發生過「兩邊改到同一支檔案撞車 / 重複做了同一件事」。出現這些再導入剛好。

## 二、它「不是」什麼 — 跟其他文件的分工（最關鍵的一節）

新團隊最常見的失敗是：把看板跟其他東西混在一起，最後變成什麼都塞的大雜燴，沒人想維護。嚴格區分這 5 種文件，各司其職：

| 文件 | 裝什麼 | 特性 |
|---|---|---|
| **WORK-BOARD（本方法）** | **live 工作狀態**：誰正在做什麼、做到哪 | 會頻繁變動、過幾天就過期 |
| FEATURE-BACKLOG（點子簿） | 未來想做但現在不做的功能 | 慢慢累積、不急 |
| TECH-DEBT（技術債簿） | 已知該還但還沒還的債 | 慢慢累積、不急 |
| handoff（單次交接） | 一次性的「換手交接信」 | 用完即丟 |
| memory（持久事實） | 永遠值得知道的事實（你是誰、設計動機、踩過的雷） | 幾乎不變、每次自動載入 |

### 為什麼進度不能塞進 memory？（最反直覺但最重要）

1. **memory 每次開新對話都會自動載入** → 塞 live 進度，會讓每個 session 一開場就吃掉一堆很快過期的雜訊，膨脹 context（浪費 token），資訊很快不準。
2. **memory 是「永遠值得知道的事實」** → 「任務做到 60%」三天後就變假的，不該跟「設計動機」放一起。

分工：**memory** 放不會變的；**WORK-BOARD** 放會變的——誰改誰負責的純文字檔。

## 三、看板的結構（建議直接照抄）

一份看板就是一個 Markdown 檔，固定包含：

1. **頂部聲明 + 分工表** — 開宗明義說「這份是 live 工作狀態的唯一來源」，附上「它不是什麼、該去哪」對照表。
2. **正規存取方式** — 寫清楚唯一正規路徑、怎麼改、改完怎麼同步。所有 session 讀寫**同一路徑的同一份檔**，建議固定放主分支。
3. **協作協定** — 看板的靈魂（見第四節）。
4. **區域地圖** — 把專案切成幾個「區域」，每區標明主要檔案。認領時一眼看出有沒有別人在做、會連帶碰到誰的地盤。
5. **🔵 進行中** — 一張表，每列 = 一個正在進行的任務。核心。
6. **📋 待辦** — 已規劃未認領的工作包，可被直接認領。
7. **✅ 近期完成** — 做完的移來這、附 commit / PR，保留一兩週再歸檔。
8. **給未來 session 的一句話** — 總結 SOP。

## 四、協作協定（核心規矩，照抄即可）

**① 開工前 3 步**
1. 看「區域地圖」+「進行中」，確認你要動的區域沒有別人在做。
2. 在「進行中」**加一列**：區域 / 任務 / 分支 / 開工日 / 今天 / 一句備註。
3. **立刻 commit + push 這個認領**（不是做完才推）→ 才開始做。

> **為什麼認領就馬上 push（搶鎖紀律）**：第①步「確認沒人 → 加一列」中間有時間差，兩個 session 可能同時讀到「沒人」然後都認領同一塊（race）。把「加一列」立刻 push，等於用 git 當搶鎖：誰先 push 成功誰得標，第二個 push 失敗、被迫 rebase 才發現撞了 → 撞車提前到「認領當下」而非「做完合併時」。

**② 做的過程**
- 每有進展，更新**你自己那列**「最後更新」+ 備註「做到哪 / 卡在哪」。
- ⚠️ **一人只改自己那列**（看板是單檔、所有 session 都寫 → 它自己就是 merge 衝突熱點）。

**③ 完工**
- 把該列移到「✅ 近期完成」，附 commit SHA / PR。

**④ 認領衝突防呆（stale 鎖回收）**
- 某列「最後更新」超過 N 天（建議 7）= 疑似那個 session 掉了。
- stale 判定**以分支最後 commit 時間為準**，不是看板編輯時間：分支一直在 commit 但忘了更新看板 ≠ 掉線。狀態腳本（`npm run board`）會自動把超過 7 天沒動的列標上 `⚠stale`。
- ⚠️ **回收前必當場 `git log -1 <分支>` 重驗 HEAD** — 別只信看板舊紀錄，否則會誤刪活躍分支。
- 確認分支無新 commit 才可改認領，備註註明「原認領 stale 回收」。

**⑤ 自動提醒（非阻擋）**
- pre-push hook 跑 `board-status.mjs --hook`：push 的 feature 分支在看板找不到 → 印一行提醒。只提醒、不擋。

## 五、怎麼讓 AI 真的會去用它（關鍵：接進「開場儀式」）

光建一份檔案沒用——AI session 不會自己想到要看。**必須把「開工前先掃看板」寫進 AI 的常駐指令裡**，它才會每次新對話都主動看。

以 Claude Code 為例，在 `CLAUDE.md` 加：

```markdown
## 對話開場 Ritual（每次新對話第一件事）
要動手做跨檔 / 功能任務前，先掃 WORK-BOARD.md 的「🔵 進行中」+「🗺️ 區域地圖」：
確認沒有別的 session 在做同一塊、不在別人分支射程內；開工 = 在「進行中」加一列認領。
純問答 / 純查詢可略過。
```

> 其他工具（Cursor 的 `.cursorrules`、各種 agent 的 rules 檔）同理。**沒接進開場儀式 = 看板形同虛設。** 完整 snippet 見 `ritual-snippets.md`。

## 六、完整走一遍（三視窗一天的劇本）

假設你同時開了三個 AI 對話視窗 A / B / C。

**09:00 — A 要做結帳重構**：A 掃看板，CHECKOUT 區、進行中是空的 → 沒人。A 加一列 `CHECKOUT｜重構結帳｜feat/checkout｜…`，**立刻 commit + push**（搶鎖），開工。

**09:30 — B 想改後台**：B 掃看板，要動 ADMIN 區，看到只有 A 在 CHECKOUT → 不重疊 ✅。B 加一列、push、開工。關鍵：B 一眼知道「別碰 `useCheckout`、`orders` 表」，因為地圖標了那是 CHECKOUT 的地盤、A 正在那。

**11:00 — C 也想改結帳裡的折扣**：C 掃看板，發現 A 已在 CHECKOUT、備註「重構中」→ 不硬上，改做別的 / 等 A 完工 / 跟 A 協調。**撞車在開工前就避免了，不是等兩個 PR 互衝才發現。**

**16:00 — A 完工**：A 把那列移到「✅ 近期完成」附 SHA。C 看到 CHECKOUT 空出來，可接手。

**隔週 — 發現殭屍認領**：看板有一列 9 天沒更新。先 `npm run board` 看那分支最後 commit 時間；若也 9 天沒動 = 疑似掉線。⚠️ 回收前當場 `git log -1` 再確認一次，真的沒新 commit 才收掉、註明「stale 回收」。

> 整個過程沒有任何「鎖」或工具強制，全靠「開工前看一眼 + 認領才動手」這個習慣。因為接進了開場儀式，每個視窗都會自動做這件事。

## 七、落地步驟

1. **建檔**：在 repo 固定位置建 `WORK-BOARD.md`（路徑固定、放主分支）。
2. **照抄結構**：複製第三節 8 個區塊（或用 `WORK-BOARD.template.md`）。
3. **畫你自己的區域地圖**：切 5～8 個區域、標明每區主要檔案。花點心思，一次畫好長期受用。
4. **寫進開場儀式**：把第五節加進 `CLAUDE.md` / `.cursorrules`。
5. **第一次認領就示範一次**：自己走一遍「認領 → 更新 → 完工」。
6. **約定 stale 天數**（建議 7）寫進協定。
7. **先上 MVP 版**：規模小就先只做「進行中」表 +「開場儀式」兩塊，等真的撞車再長出區域地圖、待辦卡、分支腳本。**過度工程會讓人懶得維護，反而失效。**

> ⚠️ **CI / 自動部署成本提醒**：看板若放 production 分支、CI 又「每 push 必 build」，則每次認領 = 一次 push = 一次 build，純文字改動也照樣燒部署額度。兩解法：① commit 帶 `[skip ci]`；② CI 加路徑過濾，只有前端程式碼變動才 build（如 Netlify `ignore = "git diff --quiet $CACHED_COMMIT_REF $COMMIT_REF -- ."`）。導入前先確認這點。

## 八、常見誤區

| 誤區 | 為什麼錯 | 正解 |
|---|---|---|
| 把進度寫進 AI memory | memory 每次自動載入會膨脹 context、且很快過期 | 進度放看板，memory 只放永久事實 |
| 看板放在某個功能分支 | 不同分支的看板會分裂 | 固定放主分支，所有人讀寫同一份 |
| 認領後不更新 | 別人無法判斷你是否還在做 | 每有進展就更新「最後更新」 |
| 多人同時重排整張表 | 看板自己變 merge 衝突熱點 | 一人只改自己那列 |
| 靠看板舊紀錄就刪別人分支 | 舊快照可能過期，誤刪活躍分支 | 回收前一律當場 `git log -1` 重驗 |
| 看板 commit 觸發整套 CI build | 純文字改動卻燒部署額度 | board commit 帶 `[skip ci]` 或 CI 加路徑過濾 |
| 什麼都往看板塞 | 變大雜燴沒人維護 | 嚴守第二節 5 種文件分工 |
| 建了但沒接進開場儀式 | AI / 人都不會主動想起來看 | 寫進常駐規則檔 |

## 九、一句話總結

> **WORK-BOARD 是一張所有開發者（包含每個失憶的 AI session）開工前都會先看、且開工就認領的純文字公佈欄。**
> 它只裝「現在誰在做什麼、做到哪」這一種會變動的資訊；其餘各有專屬文件。
> 它的價值不在檔案本身，而在於「**接進開場儀式 + 認領才動手 + stale 回收前重驗**」這三條紀律被真的遵守。
